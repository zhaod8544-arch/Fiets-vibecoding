# 飞书OKR与季度绩效管理系统个人版设计方案

## 一、项目概述

本系统面向企业内部员工，通过飞书身份登录，围绕个人季度 OKR 记录工作，借助 AI 整理成果、分析目标匹配情况并辅助季度绩效汇报。

首版服务于用户本人试用，验证真实登录、持续工作记录、AI 分析和个人汇报归档是否有用。复用现有 admin 前端和 server 后端，以实际代码为依据，不沿用已有“考试平台”描述作为业务需求。

最小闭环：真实飞书登录 → 制定个人季度 OKR → 记录周报 → AI 分析 KR 匹配情况 → 生成季度汇报与建议分 → 本人修改、填写自评分、确认归档。

首版归档属于个人自评结果。正式绩效结果需在后续版本接入 LD 审批后形成。

技术基础：Vue 3、TypeScript、Element Plus、Pinia；NestJS、Prisma、MySQL、Redis。新增业务数据通过后端持久化，真实验收路径不使用 Mock 替代飞书、AI 或数据库调用。

## 二、功能范围

### 2.1 首版必须完成

| 模块 | 功能 |
|---|---|
| 飞书身份 | 真实授权登录、首次创建关联账号、会话失效处理、退出登录 |
| 个人季度目标 | 创建季度 O 与 KR，填写衡量指标、目标值、当前值及进度，保存后直接生效 |
| 我的周报 | 记录本周工作、实际成果、阻碍和下周计划，关联 KR，自动保存、历史查询 |
| AI 分析 | 根据周报推荐 KR 关联，分析匹配情况，识别缺少证据的目标，整理成果并给出建议分 |
| 个人绩效汇报 | 随时生成季度预览，编辑汇报、填写自评分及理由，确认归档，查看历史快照 |

首版支持单人独立完成流程；其他账号即使登录，也只可访问本人业务数据。暂按单企业飞书自建应用接入设计，身份必须校验企业归属。

### 2.2 后续版本保留

日报、月报、全组织同步、直属上级关系、飞书通知、LD 审批、360 环评和正式绩效评定均不进入首版。

后续业务约定保留如下：

- 季度初由员工拟定 OKR，LD 确认后生效，调整保留版本记录。
- 平时报告和 AI 汇总不逐次确认；季度末员工确认汇报并自评打分。
- 360 环评可选组织内在职人员；LD 先审批名单，再邀请评价，然后审批结果。
- 名单和结果审批阶段均允许 LD 更换环评人；更换后补充评价，保留历史。
- 对员工匿名，LD 可见环评人身份；LD 可修改评分和意见，保留原始内容和修改原因。
- AI、自评、环评分分别展示，最终绩效由 LD 综合评定并填写理由。

## 三、核心模块设计

### 3.1 飞书登录

登录页提供“通过飞书登录”。后端生成授权请求并校验回调状态，使用授权码换取身份凭证，读取真实用户身份，校验企业归属后关联本地账号并签发系统会话。

使用企业标识与稳定用户标识关联账号，禁止凭姓名匹配。飞书应用密钥和身份交换在后端处理。授权取消或失败时返回可重试提示，不创建虚假登录状态。

首次登录进入季度目标页面，后续可进入当前季度周报。业务导航仅显示“我的季度目标”“我的周报”“我的绩效汇报”。

### 3.2 我的季度目标

按年度和季度切换。员工创建多个 O，每个 O 包含一个或多个 KR。KR 至少填写描述、衡量指标、目标值、当前值和截止日期；定性指标可填写可核查的完成标准。

目标保存后直接生效，支持修改并保留版本。进度由本人维护，AI 不自动改写实际值；指标口径不适合简单百分比时，展示原始目标值与实际值。

### 3.3 我的周报

按周查看和编辑，页面包含工作事项、成果说明、阻碍和下周计划。工作事项可关联一个或多个本季度 KR，AI 推荐关联时展示原因，本人可调整，不增加审批流程。

编辑后自动保存，显示“保存中”“已保存”或“保存失败”；失败时保留当前编辑内容并允许重试。分析只读取后端已保存的版本。同一员工每周维护一份周报，避免重复创建。

季度归属以工作事项日期为准；跨季度周报仅将对应日期的事项纳入季度分析。复制文本或同一成果反复出现时，AI 汇总需去重，不重复计算贡献。

### 3.4 我的绩效汇报

选择季度后点击“生成预览”，后端收集本人目标、进度和该季度已保存的周报，调用真实 AI 服务。页面展示汇报草稿、KR 分析、建议分与依据，以及材料不足提示。

本人可编辑汇报正文，填写百分制自评分与理由后确认归档。AI 建议分不自动替代自评分。归档必须包含本人汇报正文、自评分和自评理由。

允许随时预览，包括季度尚未结束时；不足整季度的材料明确标记为阶段性分析。重新生成先保留当前编辑版本，避免覆盖本人修改。

归档保存独立快照，后续目标或周报修改不影响已归档内容。需修订时从归档副本创建新草稿，再确认为新版本，原版本保留。

## 四、数据结构与流向

### 4.1 核心数据

| 数据 | 主要内容 |
|---|---|
| 飞书身份关联 | 企业标识、用户标识、本地账号、姓名、登录时间 |
| 季度目标及版本 | 所属人、年度季度、O、KR、指标、目标值、实际值、截止日期、生效时间 |
| 周报及事项 | 所属人、周起止日期、事项日期、成果、阻碍、计划、关联 KR、保存版本 |
| AI 分析记录 | 所属人、季度、输入快照、生成状态、输出、材料覆盖情况、模型及规则版本 |
| 绩效草稿与归档 | 本人正文、自评分及理由、引用的 AI 分析、归档时间、版本、来源快照 |

业务数据均记录所属人，后端从登录会话取得身份，不信任前端传入的用户 ID。归档快照应包含使用的目标、进度、报告与分析材料，原始记录修改后仍可核查历史结论。

### 4.2 数据流向

飞书身份经后端校验后建立账号关联；员工保存目标和周报到数据库；本人发起分析时，后端读取指定季度材料并冻结输入版本，调用 AI，校验结果后持久化；页面读取分析并支持人工编辑，最终确认保存归档快照。

前端不持有飞书应用密钥或 AI 密钥。AI 请求仅发送本次分析需要的本人目标和工作材料，不发送登录凭证或其他员工资料。

### 4.3 AI 分析与评分规则

- 匹配度回答“已记录工作与个人 KR 的相关程度”，完成度回答“实际成果达到目标的程度”，两者独立呈现。
- AI 推荐事项与 KR 的关联，展示原因与来源；手动关联优先，但不能仅凭关联关系认定目标已完成。
- 每个 KR 展示相关成果、来源周报与事项、目标值、实际值、证据缺口和分析说明。
- 汇报重点为成果、目标推进、差距与改进，不以字数、报告数量或措辞漂亮程度作为高分依据。
- 首版建议分采用百分制，由 AI 综合目标完成情况及成果证据提出，不用简单匹配度换算分数。评分规则随分析保存版本，明确区分“事实”“本人填报”“AI 推断”。
- 无目标或无工作材料时，不生成绩效分；材料覆盖不足时标记阶段性分析，证据不足以评分时不强行给数值。
- 对重复成果合并处理；AI 不能将未来计划当作已完成成果，不能自动更新 KR 实际值。
- AI 输出的来源标识必须属于本次输入快照；无效引用或结构不合法的结果不作为成功分析保存。
- 分析记录保留生成时间、材料版本、模型标识和规则版本。后续修改材料时提示分析已过时，可重新生成。
- 报告文本只作为分析材料，不能覆盖系统评分规则或触发外部操作。

AI 输出为辅助建议，员工本人确认内容并承担自评判断。评分效果需用真实周报核对，不以接口成功代替分析质量验证。

## 五、边界情况处理与验收

### 5.1 异常处理

| 场景 | 处理 |
|---|---|
| 飞书配置缺失、权限不足或授权失败 | 提示具体类别和重试入口；不生成模拟身份 |
| 授权回调重复、状态不匹配、授权码失效 | 拒绝无效请求；账号关联唯一，避免重复创建 |
| 系统会话失效 | 返回登录页，重新完成真实授权 |
| 越权访问他人目标、周报、分析或归档 | 后端拒绝，不能仅靠隐藏菜单控制 |
| 周报保存失败或多窗口编辑冲突 | 保留本次编辑内容，提示重试或重新加载，避免静默覆盖 |
| 当前季度没有目标或周报 | 引导补充资料，不伪造汇报或评分 |
| AI 未配置、超时、限流、返回格式错误 | 分析标记失败，提供重试；保留已有数据，支持人工写汇报 |
| 重复点击生成 | 同一材料版本的进行中请求合并，避免重复调用 |
| 生成期间原始材料改变 | 本次结果对应启动时的快照，提示可基于最新材料重新生成 |
| 归档期间重复请求 | 确保一次确认只创建一个版本，数据完整保存 |

### 5.2 实施顺序

1. 接通真实飞书身份和系统会话，完成账号关联与数据归属控制。
2. 完成季度 OKR、周报页面和后端持久化，先验证记录与重新登录查询。
3. 接通真实 AI，完成 KR 分析、汇报草稿、建议分和来源引用。
4. 完成人工编辑、自评分、确认归档与历史查询。
5. 使用真实账号和实际工作材料验收闭环，记录失败项并修复。

### 5.3 最小闭环验收

由用户使用真实飞书账号完成以下连续操作：登录 → 创建一个 O 与两个 KR → 保存两篇实际周报 → 更新 KR 实际进度 → 调用真实 AI 生成季度预览 → 检查成果引用和分析依据 → 修改正文、填写自评分和理由 → 确认归档 → 退出后重新登录查看。

必须核对：账号来自飞书真实授权；目标、周报、分析和归档均已写入数据库；AI 请求使用实际配置的模型服务；引用可定位到输入材料；原始材料修改后归档内容保持稳定。

两篇周报用于验证流程，不代表完整季度评估充分。材料不足时可以不输出建议分，但必须清楚解释原因。权限隔离可使用第二个真实账号或适当的后端验证方式核查。

真实验收记录包含执行时间、调用成功或失败状态、操作结果和待解决问题；记录不得暴露密钥、令牌或不必要的个人信息。只完成页面或 Mock 演示不得称为真实闭环通过。

### 5.4 联调准备与当前状态

- 飞书：企业自建应用、App ID、后端 App Secret、允许的企业标识、已配置的回调地址、身份读取所需权限和可使用该应用的真实账号。
- AI：服务地址、模型名称、后端 API Key，配置在服务器环境中；具体服务商由后续接入时确定。
- 环境：可用的 MySQL、Redis、前后端运行环境；开发与部署回调地址分别与飞书配置一致。
- 验收配合：真实授权页面需用户本人操作，应用权限及发布配置需有权限的企业管理员完成。

本文为已确认范围的设计落地文件，不代表业务代码已实现或飞书、AI 联调已通过。下一步可生成个人版 SRS，将字段、业务规则和验收要求细化为实施依据。
